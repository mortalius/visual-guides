Границы namespace: кто кому разрешает

Серая стрелка = ссылка, зелёная навстречу = разрешение
Три рукопожатия, не одно каждое пересечение границы разрешается своим механизмом
ссылка на объект ReferenceGrant
  • кто разрешаетвладелец цели ссылки
  • где живётотдельный ресурс, в namespace цели
  • что покрываетbackendRefs, requestMirror, certificateRefs
  • по умолчаниюзапрещено
привязка маршрута allowedRoutes.namespaces
  • кто разрешаетвладелец Gateway
  • где живётполе в spec самого Gateway, на листенер
  • что покрываетparentRefs маршрута
  • по умолчаниюSame - только свой namespace
привязка листенеров allowedListeners
  • кто разрешаетвладелец Gateway
  • где живётполе в spec самого Gateway
  • что покрываетparentRef у ListenerSet
  • по умолчаниюNone - запрещено

Разрешения независимы, и отказ выглядит по-разному. allowedRoutes разрешает привязать маршрут к листенеру - не совпало, и маршрут просто не аттачится: запросы к его домену отдают 404, потому что для Envoy этого маршрута нет. ReferenceGrant разрешает сослаться на объект - маршрут при этом может быть принят Gateway и всё равно отдавать 500, потому что его backendRefs смотрит в чужой namespace без гранта. Первый случай виден в статусе Gateway, второй - в статусе маршрута (ResolvedRefs=False, причина RefNotPermitted).

граница namespace ссылка через поле spec (*Ref) - пересекает границу разрешение пересечь границу (навстречу ссылке)
Грант - не универсальный ключ. Он разрешает только ссылки, и только те, что реализация умеет проверять: Envoy Gateway учитывает его в трёх случаях - backendRefs маршрута на Service, backendRef в фильтре requestMirror и certificateRefs листенера Gateway. Остальные границы закрыты жёстко, механизма разрешения там нет вовсе: политики EG (SecurityPolicy, ClientTrafficPolicy, BackendTrafficPolicy, EnvoyExtensionPolicy) целятся только в свой namespace, BackendTLSPolicy не принимает сертификаты из чужого, а у Gateway.spec.infrastructure.parametersRef поля namespace нет физически - см. слой «Ресурсы».
