Каждый Gateway реконсайлится независимо: контроллер создаёт под него собственный Deployment подов Envoy и Service типа LoadBalancer (AWS превращает его в NLB) - это база изоляции data plane. Дальше - открытый вопрос: сколько таких Gateway делят инфраструктуру между собой.

Делить инфраструктуру между Gateway или изолировать - это компромисс между изоляцией и экономией инфраструктуры, и у Envoy Gateway есть три подхода. По умолчанию (как на схеме выше) каждый Gateway получает выделенный Deployment и свой балансировщик - трафик с NLB одного Gateway не пересекается с другими. Merged сливает все Gateway одного класса в общий флот и один вход (флаг EG mergeGateways). ListenerSet решает ту же задачу общей точки входа, но иначе: один родительский Gateway, к которому команды прикрепляют свои листенеры отдельными ресурсами - это Gateway API-native механизм, и проект рекомендует его вместо mergeGateways для новых развёртываний. Переключатель под диаграммой меняет и топологию (число балансировщиков и внешних IP), и описание режима под ним.

режим 1

Gateway per Service

Топология
Каждый Gateway → свой Deployment Envoy + свой Service (NLB) + свой IP. Инфраструктуру каждому задают отдельно - spec.infrastructure.parametersRef на свой EnvoyProxy в том же namespace; отдельный GatewayClass под каждый Gateway для этого не нужен. Привязка EnvoyProxy к классу как раз не рекомендуется, когда Gateway одного класса должны получить разную инфраструктуру.
Сертификаты
Свои listeners[].tls.certificateRefs у каждого Gateway; терминация независима, свои Secret'ы.
Плюсы
  • Полная изоляция - кривой конфиг или падение одного Gateway не задевает другие.
  • Независимый сайзинг и масштабирование каждого флота.
  • Удобно разводить по разным namespace и командам.
Подводные камни
  • N балансировщиков = N× стоимость LB.
  • Разрастание внешних IP и DNS-записей.
  • Больше объектов в эксплуатации и мониторинге.
режим 2

Merged Gateways

Топология
Флаг mergeGateways: true в EnvoyProxy (через GatewayClass.parametersRef) → все Gateway класса сливаются в один Deployment + один Service/LB + один IP. Инфраструктура - одна на весь класс, и только оттуда: при mergeGateways: true per-Gateway привязка spec.infrastructure.parametersRef запрещена. Режимы 1 и 2 взаимоисключающие: выбрав свой EnvoyProxy на каждый Gateway, merged вы себе закрыли, и обратно это только через возврат привязки на класс.
Сертификаты
По-прежнему per-listener certificateRefs, но терминируются на общем флоте; нужный серт выбирается по SNI.
Плюсы
  • Один LB на весь класс - заметно дешевле.
  • Единая точка входа и один IP - проще DNS.
  • Централизованное управление инфраструктурой прокси.
Подводные камни
  • Тройка (port, protocol, hostname) должна быть уникальна по всем листенерам класса - иначе конфликт.
  • Общий blast radius: проблема одного листенера бьёт по общему флоту (noisy neighbor).
  • Масштабирование и инфра-настройки - общие на класс.
  • ClientTrafficPolicy всё равно применяется per-Gateway.
  • Gateway с непустым infrastructure.parametersRef получит Accepted=False / InvalidParameters: своей инфраструктуры у Gateway в этом режиме быть не может.
  • Механизм EG-specific, появился до поддержки ListenerSet в Gateway API.
Флаг задаётся в EnvoyProxy, на который ссылается GatewayClass.parametersRef - то есть действует на весь класс сразу и только оттуда: в EnvoyProxy, привязанном к отдельному Gateway, включить его нельзя:
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: proxy-config
  namespace: envoy-gateway-system
spec:
  mergeGateways: true   # false (по умолчанию) → свой флот на каждый Gateway
режим 3

ListenerSet

рекоменд.
Топология
Отдельные ресурсы ListenerSet прикрепляют листенеры к общему родительскому Gateway (через parentRef) → тот же общий флот и один IP, но без флага EG.
Сертификаты
Каждый набор несёт свои listeners[].tls.certificateRefs; команда управляет сертификатами независимо, выбор по SNI на общем флоте.
Плюсы
  • Gateway API-native - рекомендуемая замена mergeGateways.
  • Делегирование: платформа владеет Gateway, команды - своими листенерами и сертификатами.
  • Один LB и IP + обход лимита в 64 листенера на Gateway.
Подводные камни
  • Нужен CRD ListenerSet (Gateway API v1.5+) и разрешение через spec.allowedListeners на Gateway (по умолчанию запрещено).
  • В EG до v1.8 был за флагом XListenerSet; с v1.8 включается наличием CRD.
  • Пока не поддерживается как targetRef для политик EG.
Ментальная модель: Ingress → Gateway API что во что превращается при миграции

Gateway API разбивает монолитный Ingress на роли: инфраструктуру (кто владеет точкой входа) и маршрутизацию (куда идёт трафик) можно менять и раздавать разным командам независимо.

Ingress (один объект)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hero
  annotations:            # vendor-specific
    nginx.ingress.../rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
    - hosts: [hero.example.com]
      secretName: hero-tls
  rules:
    - host: hero.example.com
      http:
        paths:
          - path: /api
            backend:
              service: { name: app, port: { number: 8080 } }
⟶
Gateway API (роли разделены)
  • ingressClassNameGatewayClass + Gatewayкто владеет точкой входа и портами
  • tls / secretNameGateway listeners[].tlsтерминация на листенере :443
  • rules / host / pathHTTPRouteмаршрутизация, отдельный объект/владелец
  • backend.serviceHTTPRoute.backendRefs+ веса для canary
  • аннотации (rewrite, cors, auth)HTTPRoute filters + *Policyтипизированные поля вместо строк-аннотаций

Главное отличие: в Ingress всё - в одном объекте и в vendor-аннотациях; в Gateway API это типизированные ресурсы с разными владельцами. Платформенная команда держит GatewayClass/Gateway, продуктовая - свои HTTPRoute и политики.
